## 1. Executive summary

The platform has a healthy cloud lakehouse and a live website, but the **serving path is not cloud-native yet**.

Verified facts:

- Production Databricks Delta/Unity Catalog tables are current through the last completed round (Singapore, R17): 93,381 Bronze laps, 93,364 Silver laps, 92,807 lap-feature rows, and 1,679 driver rows. The exact production event count was not re-verified in this snapshot.
- The website is live at `https://f1-2026-predictions-beta.vercel.app`; `/race/18` returns HTTP 200 and renders the United States Grand Prix with 22 drivers.
- The public Supabase dashboard bundle is live: `manifest.json` generated `2026-10-23T06:05:39Z`, 194 artifacts, rounds 1–18.
- The prediction/report producer is still local: `data/outputs/laps/season=2026` contains only rounds 01–03 (2,418 rows), and `scripts/simulate_race.py` reads that local Gold to write `reports/`.
- The scheduled Databricks job’s dashboard export only **publishes** the committed `reports/` tree; it does not generate a new prediction. The job still ingests, runs DLT, trains, notifies, and exports. This split is explicitly documented in `ARCHITECTURE.md` §3.4.
- The registry champion is trained and registered, but the dashboard does not read the registry. The lap model is still untrained.
- Gmail SMTP fails from production; the job remains green because notifications are non-fatal.
- The Oct 19 and Oct 23 scheduled runs succeeded; the expected Oct 24 run has no record. The job is `UNPAUSED`; the next scheduled windows are Sunday 06:00 UTC and Monday 06:00 UTC.

**Goal:** make Databricks Delta the source of truth for the serving path, preserve the current published model until a validated replacement exists, publish a small versioned serving bundle to Supabase, and make every race-weekend step observable and repeatable.

**Non-goal:** declaring a new model more accurate, regenerating R18, or switching the website to a different model without a shadow comparison and explicit approval.

### 1.1 Next safe actions (ordered)

These are technically independent and do not change the published model or R18 numbers. They still require normal change approval before touching production.

1. **Freeze the baseline.** Do not regenerate R18, promote a model, or edit published reports. Keep the current `reports/` and registry aliases untouched.
2. **Verify the next scheduled windows.** Check the Sunday 06:00 UTC and Monday 06:00 UTC runs. If a run is missing, follow the [runbook](RUNBOOK_RACE_WEEKEND.md); do not “fix” it by regenerating predictions.
3. **Make the dashboard source explicit.** Set `F1_DASHBOARD_DATA_BASE_URL` to the public Supabase manifest base and `F1_DASHBOARD_DATA_STRICT=1` in Vercel. This is a serving-config change only.
4. **Make the schedule explicit and add a retry.** Replace `FRI-MON` with `FRI,SAT,SUN,MON` and add a post-race retry window. This changes no prediction.
5. **Fix notification delivery.** Use an HTTPS relay; do not rely on Gmail SMTP from Databricks Free Edition. Make `0/N channels` visible.
6. **Add freshness and health checks.** Prove that the expected round is in Delta, the manifest, and the live page; alert when it is not.
7. **Build cloud inference in shadow.** Generate the current product from Databricks and compare it to the published R18 bundle. Do not cut over until the diff is understood and approved.
8. **Cut over with rollback ready.** Point Vercel at the new release prefix only after shadow parity; keep the previous prefix.
9. **Only then decide on model/data parity.** Rebuilding 2026 Gold and regenerating R18 is a separate, explicitly approved phase.

## 3. Scope

### In scope

- Move the **prediction generation and dashboard export** behind Databricks compute.
- Keep Delta/Unity Catalog as the source of truth for features and predictions.
- Preserve the current published 70-feature model until a validated replacement exists.
- Define a small, versioned serving bundle and a manifest contract.
- Make the dashboard consume the cloud bundle explicitly, with strict validation.
- Make scheduling explicit and observable, including a post-race retry.
- Replace or bypass the failing Gmail SMTP path with a free HTTPS relay.
- Add data-freshness, artifact, and notification health checks.
- Document the runbook, rollback path, and operational limits.

### Out of scope

- Claiming improved accuracy or regenerating R18 without a separate approval.
- Replacing the `@champion` model without shadow comparison and promotion-gate evidence.
- Real-time/live timing, in-race telemetry, or a UI redesign.
- Paid services, GPU serving, provisioned throughput, or a commercial Databricks plan.
- Moving the whole Gold table into the Next.js build.
- Rewriting the historical reports or changing their published values.

### Constraints and assumptions

- Databricks **Free Edition** remains the compute/lakehouse: serverless-only, one `2X-Small` SQL warehouse, max 5 concurrent job tasks, one active pipeline per pipeline type, no GPUs, restricted outbound internet, non-commercial use, no SLA.
- Supabase free storage (1 GB) remains the object store for the dashboard bundle and FastF1 cache.
- Vercel Hobby remains the frontend.
- The current 70-feature local pipeline is the product model to preserve for the first cloud cutover.
- The cloud `lap_features_gold` table exposes 13 features; it is **not** interchangeable with the local 70-feature frame.
- No credentials, tokens, or secret values belong in documentation, logs, or artifacts.

### Security and access

- The Supabase bundle is public by design. Publish only aggregate predictions, standings, summaries, and images; never raw telemetry, credentials, PII, or internal logs.
- Databricks secrets live in the `f1_secrets` scope; local development uses `.env`. Rotate the Supabase S3 pair with `scripts/rotate_supabase_s3_keys.py` and record the rotation; never commit the values.
- Vercel only needs the public bundle base URL and the strict flag; it must not hold a Databricks token or warehouse credential.
- Do not log signed URLs, access keys, session tokens, or full request headers.
- The manifest and release prefix are public artifacts; treat them as immutable and never place secrets in them.

## 4. Architecture decision record (ADR-001)

### Decision

Use **Databricks Delta/Unity Catalog as the source of truth**, run **batch inference inside Databricks**, write a compact `dashboard_round_predictions` table and a versioned JSON/CSV bundle, and publish that bundle to **Supabase Storage** for the Vercel build. Do not query Delta directly from Next.js. Do not generate production predictions on the local filesystem.

### Options considered

| Option | Description | Verdict |
|---|---|---|
| A. Keep local Gold + committed reports | Current behavior | **Rejected.** Not cloud-native, not reproducible from Delta, stale by 14 rounds, and the scheduled job cannot predict |
| B. Query Delta directly from Next.js | Dashboard talks to Databricks SQL/API at build or request time | **Rejected.** Adds credentials, latency, warehouse cost, Free Edition limits, and a runtime dependency |
| C. Databricks batch inference + object storage | Job reads Delta, writes compact artifacts, Supabase serves the static site | **Chosen.** Fits Free Edition, preserves the static frontend, supports rollback and provenance |
| D. Re-platform to BigQuery/Snowflake | Move the warehouse | **Rejected.** Re-platforming cost and loss of DLT/MLflow integration; not justified for a free project |

### Decision details

- **Source of truth:** Delta tables in `main.f1_2026_prod`; the local `data/outputs` tree is development-only.
- **Model preservation:** first cutover keeps the current 70-feature published model. The model must run in the cloud against a cloud-accessible copy of its feature inputs. Do not silently replace it with the 4-feature aggregate champion or the 13-feature lap contract.
- **Serving contract:** one record per `(season, round, driver)` with:
  - `schema_version`
  - `season`, `round`, `event_name`, `driver`, `team`
  - `predicted_laptime_xgb_s`, `predicted_laptime_lgb_p05_s`, `predicted_laptime_lgb_p50_s`, `predicted_laptime_lgb_p95_s`
  - `model_name`, `model_version`, `feature_contract_version`
  - `source_round`, `generated_at`, `run_id`, `status`
- **Bundle contract:** `manifest.json` written last; artifacts relative to the release prefix; versioned release directory; no partial bundle is visible as current.
- **Dashboard:** `F1_DASHBOARD_DATA_BASE_URL` points at a specific release prefix; `F1_DASHBOARD_DATA_STRICT=1` fails the build on a missing/invalid bundle.
- **Notifications:** do not rely on SMTP from Databricks Free Edition. Use an HTTPS relay (Supabase Edge Function or GitHub Actions) for email. A zero-channel dispatch is observable, not silently successful.
- **Scheduling:** explicit days plus a post-race retry; freshness checks fail loudly when the expected round is absent.

### Consequences

- A new Databricks task/job must be built and tested.
- The current 70-feature pipeline must be packaged for cloud execution, or a validated replacement path must be chosen. This is a decision gate, not an assumption.
- The dashboard build becomes dependent on the release prefix, not on the git checkout.
- Rollback becomes a matter of pointing at the previous release prefix.
- The system remains batch/static; it does not become real-time.

### Revisit triggers

- A validated model replacement becomes available.
- Free Edition quotas or egress policies change.
- Supabase storage/egress becomes insufficient.
- The product requires live/in-race updates.
- The dataset grows beyond a single-node pandas batch.

## 5. Target architecture

```text
FastF1 / external sources
        |
        v
Unity Catalog Volume: raw_telemetry
        |
        v
DLT: Bronze -> Silver -> Gold (Delta, Unity Catalog)
        |
        +--> aggregate/lap training + registry (existing)
        |
        +--> Phase 22 batch inference
                 |
                 v
        dashboard_round_predictions (Delta)
                 |
                 v
        exporter: compact JSON/CSV + manifest.json
                 |
                 v
        Supabase Storage: dashboard/2026/releases/<release-id>/
                 |
                 v
        Vercel build: F1_DASHBOARD_DATA_BASE_URL + STRICT=1
                 |
                 v
        Public dashboard

Scheduling:
  Databricks job -> ingest -> DLT -> inference -> export -> notify
  Post-race retry if FastF1 data is not yet available
```

### 5.1 What moves where

| Concern | Today | Target |
|---|---|---|
| Feature source | Local `data/outputs/laps` | Delta tables / cloud-accessible feature snapshot |
| Prediction | Local `scripts/simulate_race.py` | Databricks batch inference task |
| Report assembly | Local `reports/` | Cloud exporter writes release bundle |
| Serving | Git + Supabase export of committed reports | Supabase release prefix, manifest last |
| Model provenance | Mostly implicit | Explicit model/version/feature-contract metadata |
| Post-race update | Manual local run + commit | Scheduled cloud inference + export |
| Email | Gmail SMTP from Databricks | HTTPS relay with observable delivery |

### 5.2 What remains local

Local execution is allowed for development, tests, and backtests only. It must not be the production source for the website. The committed `reports/` tree remains a local-development fixture and an emergency historical reference, not a production producer.

### 8.2 Acceptance criteria

The following must all be true before claiming “cloud-native serving”:

- [ ] The production prediction path has **no read of `data/outputs/laps`**.
- [ ] The production bundle is generated from Delta/cloud inputs, not from a developer’s committed `reports/` tree.
- [ ] Every artifact carries model, model version, feature contract version, source round, and generation time.
- [ ] The manifest is written last; a rerun is idempotent; a partial bundle cannot become current.
- [ ] The dashboard build fails closed when `F1_DASHBOARD_DATA_STRICT=1` and the bundle is missing/invalid.
- [ ] A completed race produces a new manifest round and a live page within the agreed SLO.
- [ ] A missing scheduled run, a failed ingest, a failed export, and a zero-channel notification are all observable.
- [ ] A previous release can be restored without changing code.
- [ ] No model promotion or R18 regeneration happens without a separate, documented validation.
- [ ] No accuracy claim is made unless it was measured.

### 8.3 What does **not** count as validation

- A green job with no new round.
- A page that returns HTTP 200 but is serving an old manifest.
- A notification task marked `SUCCESS` with `0/1 channels`.
- A local rerun that is not reproduced in the cloud.
- A model improvement claimed from a reconstruction metric.
- A manual file copy that bypasses the release/manifest contract.

## 9. Rollback and incident response

### 9.1 Release rollback

Target layout:

```text
dashboard/2026/releases/<UTC timestamp>-<short sha>/manifest.json
dashboard/2026/releases/<UTC timestamp>-<short sha>/<artifacts>
```

> **Current limitation:** the existing publisher writes to `dashboard/2026` and has no versioned prefix. P22-A5 introduces the layout above; until then, preserve the last known-good bundle before any republish and do not treat prefix rollback as available.

`F1_DASHBOARD_DATA_BASE_URL` points at one release prefix. Rollback:

1. Identify the last known-good release prefix.
2. Update the Vercel environment variable to that prefix.
3. Trigger a Vercel rebuild.
4. Verify the expected round and 22 drivers on `/race/<round>`.
5. Record the rollback in the incident log.

Do not delete the old release prefix during an incident. Do not edit the manifest by hand.

### 9.2 Inference/model rollback

- Stop the export before changing a model.
- Keep the previous `@champion` alias and previous release bundle.
- Do not promote a candidate to cover a serving bug.
- If a model change caused the issue, restore the previous release and model alias; rerun the validation gate.

### 9.3 Schedule/notification rollback

- Restore the previous cron or disable the new retry.
- Use the documented manual job run only when the current job is known good.
- For notifications, disable the failing channel and use the documented secondary; do not claim delivery.

### 9.4 Severity

| Severity | Example | Response |
|---|---|---|
| SEV1 | Site down, wrong round, or corrupted bundle | Roll back immediately; preserve evidence; notify owner |
| SEV2 | No post-race update; ingest failed; missing run | Manual check; run fallback only if safe; open incident |
| SEV3 | Notification failure; stale non-critical artifact | Record, fix in next window; site remains primary |
| SEV4 | Cosmetic/missing optional artifact | Backlog |

## 11. Free-tier operations and budget

### 11.1 Service limits that affect the design

| Service | Limit / behavior | Design consequence |
|---|---|---|
| Databricks Free Edition | Serverless-only; one `2X-Small` SQL warehouse; max 5 concurrent job tasks; one active pipeline per type; no GPUs; restricted outbound internet; non-commercial; no SLA | Keep the job small; avoid parallel task explosion; no SMTP; test egress; treat runs as best-effort and alert on misses |
| Supabase Storage | Free 1 GB; S3-compatible; public bucket currently used | Store only the dashboard bundle and cache; monitor; do not store the lakehouse here |
| Cloudflare R2 (optional) | Free 10 GB; no egress; S3-compatible | Best free upgrade for object storage, but test reachability from Free Edition before adopting |
| Vercel Hobby | Free/non-commercial; static/ISR | Keep the build static; fetch a small bundle; no server-side warehouse query |
| GitHub Actions | Free for public repos; minutes limited for private | Use for CI and, if needed, the notification relay |
| Supabase Edge Functions | Free invocation tier | Use as an HTTPS relay if Databricks egress blocks SMTP/provider APIs |

### 11.2 Cost guardrails

- No paid model-serving endpoints; batch inference only.
- No extra SQL warehouse; stop it when idle.
- No duplicate scheduled jobs; one scheduler.
- Publish small JSON/CSV/PNG artifacts, not raw laps.
- Keep one release prefix per race; prune only after a retention decision.
- Never use a paid email provider without an explicit budget decision; use the free tier.

### 11.3 Data budget

- The production Delta tables are small relative to Free Edition storage.
- The FastF1 cache is roughly 113 MB; the dashboard bundle is small (194 artifacts, mostly JSON/CSV/MD).
- Supabase’s 1 GB free bucket is sufficient for the current bundle plus cache, but it is not a data lake.
- If the cache grows, move the cache to R2 or prune old seasons; do not mix cache retention with dashboard retention.

### A.3 Contract invariants

- `file_count == len(files)`.
- The manifest is written **after** every file it references.
- One row per `(season, round, driver)`; no duplicate driver rows.
- The expected driver set for the event is present; currently 22 for a full grid.
- Required numerical fields contain no `NaN`/`null` values.
- `status` is one of `shadow`, `published`, `rolled_back`.
- Timestamps are UTC ISO-8601.
- A release prefix is immutable; a correction creates a new release.
- The public bundle contains no secrets, credentials, PII, or raw telemetry.
- The dashboard can fetch every file listed in `files` from the same release prefix.
